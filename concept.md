Okay, here's my summary of how my system works. So on the far left we have the human zone. So this is where the human works, this is where the actual shipable code lives as well. Inside the human zone we author goals, the goals are what we hand over to agents. Also part of the human zone is the hierarchical context documentation. That's what provides agents context of the architecture and the structure of the code base. In addition to goal authoring, shipable code, and the hierarchical context documentation, there's also user experience testing. Parts where automated oracles can't fill the gap, and a human has to come and in and click buttons.

Part of the process of goal authoring is checking whether the goal actually makes sense and is achievable. That's where the scout system comes in. So scout is agent-led and it's typically a throwaway code repository or folder where the agent can experiment. There's three components to this. The agent can research relevant prior art on the web or in organizational notes based on the goal and what the human is trying to achieve. The agent can actually spike out real executable code as throwaway prototypes or spikes to prove the path, and also we can run a multi-agent debate on the goal using the debate battle framework. The result is insights and goal refinement, which gets fed back into the human zone.

Once the goal is ready to be passed out to an agent to implement, that's when the human replay process comes in. We don't implement directly inside of ship code artifacts. We take a copy using the prep skill, which gets copied over into a sandbox folder for the agent to work in. 

The root agent is the implementer. That agent's job is to write code. It takes the goal and implements the functionality. It does it phase by phase, not all in one go. Everything the agent implements, it has to prove that it works empirically using an oracle. Oracles could be unit tests, integration tests, deterministic simulation testing or chaos tests. Underpinning all of those tests is tracing and metrics, which the agent uses to definitively prove the internal behaviour of the system. What's important to internalize here is that the quality of the code that the agent can write is directly proportional to the falsification depth of the oracles. The oracles need to prove that what the agent wrote was wrong. That's the only thing that gives agents proper feedback to correct their code mistakes.

Oracles rely on a realistic test environment. This could be just the local box running a Linux machine that runs unit tests or integration tests. Or it could be other machines on a LAN, like a cluster of RaspberryPis. Or it could be deployed to a real cloud environment to test with actual cloud platform as a service components. Mocking is an anti-pattern and should be used sparingly.

Once a phase is done by the implementer, it gets handed off to a sub-agent for an adversarial review. The sub-agent could run tests against oracles, or it could just read the code directly and evaluate based on the goal. Its job is a fresh pair of eyes and a critical lens on what was built, but passing that output directly back to the main agent that's implementing the code is a mistake. It results in gold plating. So a second sub-agent needs to be run, which takes the input from the adversarial review and triages it to work out what needs to be done now, what can be deferred, what can be deleted, or what needs delegation back to the human for review. 

Things that got deferred, or delegated go to a triage scraps dumping zone. Deleted items just get dropped and not recorded. These are the leftovers that for things that were identified in the adversarial review, but the triage agent decided that it's not worth implementing right now in this current phase. They could still be picked up by the agent that's implementing the code in a following phase, or they could just be deferred entirely back to the human zone, depending on how relevant it is to the goal.

This process inside the sandbox is a loop. Implementer, adversarial view, triage agent. While this is happening and the phases are being built out, there are two documents that are being kept up to date. The first is session state, which is a mutable document that the main agent keeps up to date with what it's currently working on. The second document is an append only, immutable progress document which captures the history of what the agent did to implement the goal.

Typically, the work done in a sandbox is autonomous, and the agent shouldn't interrupt the human. The only exception is when triage identifies something that needs delegation to the human, a critical design decision, or if the agent requires user experience testing, things that can't be proven with empirical oracles. Stuff that humans need to actually do, like clicking buttons and viewing screens.

At the end, once the goal is implemented, the loop stops. Then, the agent generates a replay guide that's used to replay the code back into the human zone, shippable code base. We don't ship sandboxed agent-led code straight to prod.

This is where the real work comes in for the human. The human needs to use the vsCode extension for Human Replay to replay back the agent implemented code using the generated replay guide. Divergence is expected. We expect the human to look at the code that agent wrote, make changes, or push it back to the sandbox for another iteration. 

Once the human folds back in the implemented code, the hierarchical context docs are updated, and the code is shipped to prod. The goal.md and other md artifacts are deleted. Code is the design, code is the source of truth.

All agent work is guided by a set of skills. There's persona-driven design, which outlines our purpose, why the goals exist and who we're building for. Then there's coding style, because not every way of writing code in a language is the right way to write code. There are some ways that are better than others. Then there's writing style. The default writing style for LLMs is terrible. It needs customization. Same with unit testing. Unit testing needs discipline, otherwise they sprawl and it becomes difficult to maintain. Also comments. LLMs love to comment everything, but actually the code is the source of truth and comments drift. So we minimize comments. Make them only comment things that really need commenting. And finally, performance discipline. LLMs take shortcuts. They don't think about performance when they're building out function by function deep in an implementation loop.
